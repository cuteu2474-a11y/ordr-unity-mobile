## 이정표

- **60~70차: 첫 플레이 가능 시험판 목표.** 주요 유닛을 뽑아 조합하고 라운드를 진행할 수 있는 코드 상태. 실제로 '플레이 가능'하다는 판정은 사용자 승인 후 APK 설치/실전 확인을 거쳐야 한다.
- **85~95차: 주요 시스템 완성판 목표.** 핵심 유닛/스킬·보상·시설·저장 기능의 작동 경로가 연결된 상태.
- **100차 전후(현실적 90~110차): 완성 후보.** 모든 원본 효과의 100% 동등성을 자동으로 보장하지 않는다. 기기 검증과 차이 목록 정리가 남으면 완성으로 선언하지 않는다.

차수당 목표는 **조합 10~15건**, **유닛 기본 기능 10~15종**, **고유 스킬/패시브 15~25개**다. 공통 엔진 한 번으로 더 많이 연결되면 범위를 합치고 차수도 줄인다. 고난도 JASS 콜백이나 원본 증거 누락이 있으면 근거 없는 임시 구현 없이 재조정한다.

## 운영/완료 판정 규칙

1. 기존 구현·공통 효과·기존 문서부터 조회하고 **중복 구현을 제외**한다. 새로운 브랜치·워크플로를 만들지 않고 main만 쓴다.
2. 원본 공격력·쿨타임·스킬 확률·조합 규칙을 임의 변경하지 않는다. **원작 원리가 아니라 실제 결과 일치**를 목표로 하지만 자료가 부족한 경우 구현한 척하지 않는다.
3. 기능을 하나씩 자잘하게 수정하거나 매번 검사하지 않는다. 공동 거래·전투·상태·획득 엔진을 먼저 구축하고 차수별 묶음으로 적용한다.
4. 기능 상태를 **자료 확인 / 코드·UI 매핑 / 실제 실행 경로 연결 / Unity 검증 / Android 실기 검증**으로 구분한다. 테스트 코드만 작성한 상태는 실제 통과가 아니다.
5. **Python, Unity EditMode, 시뮬레이터, APK 빌드는 사용자가 명시적으로 요청할 때만 실제 실행**한다. 계획표 자체는 테스트 실행 허가가 아니다.
6. GitHub 개발 커밋은 되도록 차수당 1개, 기존 문서 4종(START_HERE/CODE_MAP/PLAYABLE_ROADMAP/인수인계)을 함께 최신화한다. main 푸시로 자동 GitHub Actions가 시작됐는지만 확인하고 결과 대기·조회 없이 즉시 응답을 종료한다.
7. 검증에서 주요 결함이 나오면 지정 차수보다 **원인·연관 오류·근본 수정·회귀 방지**를 우선하며, 계획 범위를 조정한다.
